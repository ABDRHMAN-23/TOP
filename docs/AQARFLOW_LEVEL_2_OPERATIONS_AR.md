# المستوى الثاني — عمليات المبيعات والمتابعة ومعاينات العقارات

## نطاق التنفيذ

هذا المستوى يضيف مسار تشغيل يومي فوق CRM المستوى الأول، دون إرسال رسائل تلقائي أو إنشاء موارد/تغيير قاعدة Supabase الحية:

- مركز عمليات على `/aqarflow-operations` لإنشاء المهام وعرضها وإكمالها أو إلغائها.
- أنواع مهام: متابعة، اتصال، إرسال معلومات، معاينة، مستندات، وأخرى؛ مع أولوية وموعد وملاحظات وحالة.
- جدولة المعاينات وربطها بعميل وعقار اختياري، وموقع، وبداية ونهاية، ومنطقة زمنية IANA.
- حالات المعاينة: مجدولة، مؤكدة، مكتملة، ملغاة، ولم يحضر العميل.
- مزامنة `aqarflow_crm_contacts.next_follow_up_at` تلقائيًا إلى أقرب مهمة نشطة. تنفذها قاعدة البيانات في trigger كي تبقى صحيحة عند إنشاء المهمة أو تعديلها أو إكمالها أو إلغائها.
- منع حجز معاينتين نشطتين متداخلتين للعقار نفسه داخل مساحة العمل، بما في ذلك الطلبات المتزامنة، بقفل معاملات في PostgreSQL وفحص تعارض قبل حفظ التغيير.
- APIs محمية بجلسة مستخدم وتحدد `owner_user_id` في كل قراءة وكتابة. لا تمنح هذه الجداول صلاحية Data API مباشرة لـ`anon` أو `authenticated`؛ يمر الوصول عبر الخادم فقط.
- التحقق من معرفات UUID، وأطوال النصوص، والأنواع، والحالات، وصحة التواريخ، والمنطقة الزمنية، ومدة المعاينة. حذف سجل التشغيل غير متاح من الواجهة؛ المهام والمواعيد تُلغى لتبقى حالتها المسجلة.
- اختبارات عقد لـAPI والتحقق، واختبارات PostgreSQL للهجرات وعزل المؤسسات، ومزامنة المتابعة، ومنع تعارض المواعيد؛ وتشغيلها في CI.

## تشغيل الاختبارات

CI يطبق الهجرات الست بالترتيب على قاعدة PostgreSQL مؤقتة، ويشغّل اختبارات العقد والبناء:

```bash
npm run test:aqarflow:operations
npm run test:aqarflow:migration
bash scripts/test-aqarflow-migrations.sh
npm run build
npm run build:cloudflare
```

اجتياز PostgreSQL المؤقت وCI لا يغني عن تطبيق الهجرة على مشروع Supabase تطويري حقيقي والتحقق من الـ grants وRLS والمشغلات عليه.

## تطبيق قاعدة البيانات في بيئة تطوير

طبّق الملف السادس بعد الملفات `20261010000200` إلى `20261010000500` على مشروع تطوير منفصل يحتوي مخطط Auth و`team_memberships` الخاصين بـTOP. تحقق من وجود الجدولين، ومفعول RLS وFORCE RLS، وعدم وجود grants مباشرة إلى `anon` و`authenticated`، وعمل trigger المتابعة ورفض الموعد المتداخل. لم تطبق هذه الهجرة على الإنتاج ولا على مشروع Supabase بعيد ضمن هذا التنفيذ.

## حدود مقصودة

- المركز يسجل المهام والمواعيد ويعرض المتأخر منها داخل المنتج؛ لا يدّعي إرسال تذكيرات SMS/WhatsApp أو بريد إلكتروني في الخلفية، إذ لا يوجد مجدول تشغيلي مربوط ومتحقق منه هنا.
- جدولة المعاينة لا ترسل رسالة للعميل ولا تدّعي أنها تأكدت منه؛ يجب على المستخدم تأكيد الموعد ثم استخدام مسار WhatsApp المعتمد يدويًا.
- لا نعد بنجاح نشر فعلي على Cloudflare/Vercel لمجرد نجاح البناء.
- تبقى بوابات المستوى الأول: إعداد Meta وتجربة فعلية من WABA تطويري، تطبيق هجرات على Supabase تطويري، وتقييم Promptfoo على endpoint مصادق عليه.
- هذا المستوى لا يدمج حرفيًا تطبيق DeskcommCRM المستقل، ولا يبدل جذر TOP/QUVOTO أو قاعدة إنتاجه.

## معيار الإغلاق

يُعلن المستوى الثاني جاهزًا برمجيًا بعد نجاح تشغيل CI على الرأس الأخير. ولا يُعلن جاهزًا للإنتاج إلا بعد تجربة الوظائف على قاعدة تطوير حقيقية، والتحقق من عزل مالكين مختلفين، واختبار عدم تعارض المعاينات والـfollow-up trigger، وإكمال بوابات التشغيل الحي المذكورة أعلاه.
