# خطة تحويل TOP (QUVOTO) إلى AqarFlow AI — مراجعة ما قبل التنفيذ

**الحالة:** تحضير فقط. لم تُطبق أي تغييرات على قاعدة الإنتاج ولم تُحذف بيانات.  
**المستودع:** `ABDRHMAN-23/TOP`  
**قاعدة Supabase:** `TOP` (`djpfjbjjybpquvzacmtj`) — منطقة `ap-southeast-2`  
**الفرع:** `migration/aqarflow-ai` مشتق من `main`.

## 1. حدود التفويض

مسموح في هذه المرحلة:
- القراءة والفحص فقط لقاعدة الإنتاج.
- توثيق المخاطر والخطة في هذا الفرع.
- إعداد تغييرات الكود لاحقًا على الفرع المنفصل فقط، بعد مراجعة الملفات ذات الصلة.

غير مسموح:
- تنفيذ DDL/DML أو migrations على قاعدة الإنتاج.
- حذف أو تعديل سجلات أو ملفات Storage أو المستخدمين.
- نشر Worker/موقع أو تغيير الأسرار أو إعدادات الإنتاج.
- إنشاء مشروع/فرع/موارد مدفوعة في Supabase دون عرض التكلفة والحصول على موافقة منفصلة.
- دمج الفرع أو تغيير `main` دون موافقة مستقلة.

## 2. نتائج القراءة فقط (2026-10-09)

- المستودع الحالي هو تطبيق **QUVOTO/VoiceQuote** للمقاولين وعروض الأسعار الصوتية، وليس منتجًا عقاريًا.
- قاعدة البيانات PostgreSQL 17.6.1، وحالتها المعلنة `ACTIVE_HEALTHY`.
- يوجد 25 جدولًا في `public`، وعدّ كل جدول أعاد صفر صفوف وقت الفحص. هذه نتيجة لحظية ولا تُعد ضمانًا بعدم وجود بيانات في أنظمة أخرى.
- `auth.users` أعاد صفر مستخدمين وقت الفحص.
- توجد 59 سياسة RLS؛ RLS مفعّل على 25/25 جدولًا عامًا، لكن FORCE RLS مفعّل على 0/25. يلزم تدقيق تعريفات السياسات والأدوار قبل التشغيل العقاري.
- توجد حاويتان عامتان في Storage: `business-logos` و`quote-photos`. لم يعثر استعلام `storage.objects` على كائنات وقت الفحص؛ يجب إعادة التحقق من خلال Storage API قبل الترحيل.
- قائمة migrations المسجلة تتضمن تغييرات متعلقة بعروض الأسعار والفواتير والفرق والإحالات والفوترة. يجب حفظ هذه القائمة ومطابقتها مع ملفات migrations في GitHub قبل أي تغيير.
- لم تُراجع بعد كل سياسات RLS وسياسات Storage والـ triggers والـ functions والـ secrets بالتفصيل.

## 3. مخاطر رئيسية

1. **استبدال منتج عامل:** حذف واجهات QUVOTO دفعة واحدة قد يكسر المسارات الحالية وروابط العملاء والاشتراكات.
2. **اختلاف نموذج البيانات:** العقارات والعملاء المحتملون والمكاتب والمحادثات والمعاينات لا تطابق عروض الأسعار والفواتير الحالية.
3. **عزل المؤسسات:** يلزم تعريف tenant/workspace boundary واختبار الوصول المتبادل بين مكاتب العقارات، لا نسخ السياسات الحالية دون تحليل.
4. **الأسرار والتكاملات:** إعدادات Cloudflare تشمل أسماء أسرار لخدمات الذكاء الاصطناعي وSupabase والفوترة؛ يجب عدم نسخ قيم الأسرار إلى Git أو سجل المحادثة.
5. **الملفات:** الحاويات الحالية عامة؛ لا يجوز تحويلها أو تغيير صلاحياتها دون جرد واختبار الروابط وسياسات الوصول.
6. **الرجوع:** الرجوع إلى commit سابق لا يعكس تلقائيًا تغييرات قاعدة البيانات أو Storage؛ يجب أن تكون خطة الرجوع منفصلة لكل طبقة.

## 4. النسخ الاحتياطي المطلوب قبل الترحيل

**لم تُنشأ نسخة احتياطية خارجية حتى الآن.** أدوات الاتصال المتاحة في هذه الجلسة لا توفر عملية موثوقة لتصدير ملف `pg_dump` كامل قابل للتنزيل والتحقق من استعادته، لذلك لن أزعم أن النسخ الاحتياطي اكتمل.

قبل أي تعديل إنتاجي:
1. أنشئ تصدير PostgreSQL كاملًا يشمل schema وdata، وتعريفات الوظائف والسياسات والـ triggers، باستخدام Supabase CLI/`pg_dump` من بيئة موثوقة أو وسيلة تصدير موثقة.
2. صدّر تعريفات Auth وإعدادات المشروع المتاحة، دون محاولة استخراج كلمات مرور أو أسرار مخفية.
3. جرد كائنات Storage وتنزيل كل كائن فعليًا، مع حفظ manifest يحتوي bucket/path/size/content-type. لا يكفي نسخ صفوف metadata.
4. احتفظ بقائمة migrations وcommit SHA وملفات إعدادات النشر، مع تخزين الأسرار في مدير أسرار آمن منفصل.
5. خزّن النسخ في وجهة خارج المشروع، مشفرة ومقيدة الوصول، وتحقق من checksum وحجم الملفات.
6. نفّذ استعادة تجريبية في قاعدة منفصلة موجودة مسبقًا ومصرّح بها؛ لا تنشئ موردًا مدفوعًا جديدًا دون موافقة التكلفة.
7. وثّق نتيجة الاستعادة وعدد الجداول والصفوف والسياسات والملفات، ثم اطلب موافقة منفصلة قبل أي تغيير إنتاجي.

لا تضع connection strings أو مفاتيح service role أو أسرار Cloudflare داخل هذا المستودع.

## 5. خطة التنفيذ المقترحة

### المرحلة A — جرد واختبارات (دون تغيير قاعدة الإنتاج)
- توثيق commit الحالي والملفات والمسارات والمكونات والتكاملات.
- مراجعة migrations الفعلية في GitHub مقابل سجل migrations في Supabase.
- تدقيق RLS وGRANTs والوظائف والـ triggers وStorage policies.
- توثيق مسارات تسجيل الدخول، الفرق، الفوترة، Webhooks، المهام الخلفية، والملفات.

### المرحلة B — تصميم AqarFlow
- كيانات: workspaces/offices، memberships/roles، properties، leads، conversations، messages، appointments/viewings، follow-ups/tasks، consent/audit events، integrations.
- فرض عزل المكتب في قاعدة البيانات والتحقق من كل سياسة باستخدام اختبارات سلبية وإيجابية.
- إبقاء مفاتيح واتساب والذكاء الاصطناعي والخدمات الخارجية server-side فقط.
- وضع حدود للاستخدام والتكلفة، وتسجيل الموافقات قبل إرسال رسائل خارجية أو تنفيذ إجراءات مؤثرة.

### المرحلة C — الكود في الفرع فقط
- إزالة/استبدال واجهات QUVOTO على الفرع المنفصل تدريجيًا، لا على `main`.
- عدم تغيير `lib/supabase/public-config.ts` إلى مشروع آخر قبل تأكيد هوية الهدف وخطة الربط.
- إضافة migrations كملفات مراجعة فقط؛ لا تطبيق تلقائي على الإنتاج.
- تشغيل lint/typecheck/build/tests المتاحة وتوثيق أي فشل.

### المرحلة D — مراجعة ما قبل النشر
- مراجعة diff كاملًا، اختبارات عزل المكاتب، auth، سياسات Storage، webhook signatures، rate limits، secret scanning.
- إثبات استعادة النسخة الاحتياطية وخطة الرجوع.
- تقديم تقرير بالنتائج والتكلفة والمخاطر المتبقية.
- طلب موافقة ثانية صريحة قبل تشغيل أي migration أو تغيير إعدادات/بيانات الإنتاج.
