# تقرير جرد المستودع وقاعدة البيانات — AqarFlow AI

**تاريخ الفحص:** 2026-10-09  
**مستودع العمل:** `ABDRHMAN-23/TOP`  
**فرع التوثيق:** `migration/aqarflow-ai`  
**قاعدة Supabase المفحوصة:** `TOP` — فحص قراءة فقط

> هذا تقرير تحضيري وليس اعتمادًا أمنيًا نهائيًا. لم تُنفّذ أي كتابة في قاعدة البيانات، ولم تُحذف أو تُعدّل بيانات، ولم يتم النشر.

## 1. خلاصة تنفيذية

المستودع الحالي هو QUVOTO/VoiceQuote، وهو تطبيق Next.js لعروض أسعار المقاولين من ملاحظات صوتية، وليس CRM عقاريًا. التحويل ليس تغيير اسم فقط؛ يتطلب إعادة تصميم نموذج البيانات والصلاحيات والمسارات والواجهات والتكاملات.

**أهم مانع قبل أي تغيير في قاعدة البيانات:** لا يوجد في جذر المستودع مجلد `supabase/` أو ملفات migrations المصدرية، بينما تسجل قاعدة الإنتاج 17 migration. يلزم مطابقة تلك السجلات مع تاريخ Git/مصدر migrations مفقود قبل اعتبار إعادة البناء أو الاستعادة قابلة للتكرار.

## 2. جرد ملفات التطبيق

### البنية الحالية
- `app/`: واجهات الصفحات وواجهات API.
- `app/api/`: تشمل وحدات `analyze` و`quotes` و`billing` و`workspace` و`team` و`referrals` و`notifications` و`advisor` وغيرها.
- `components/`: مكونات واجهة خاصة بالمنتج الحالي، منها `QuvotoLogo` و`DailyBrief` و`ReferralChallenges`.
- `lib/supabase/`: عميل المتصفح والخادم وعميل امتيازات مرتفعة وملف إعداد الاتصال.
- `scripts/`: اختباران مخصصان متعلقان بذكاء الأسعار ومتطلبات المستشار.
- `wrangler.jsonc`: إعداد نشر Cloudflare Worker اسمه `to`، مع R2 bucket اسمه `voicequote-opennext-cache` وخدمة self-reference اسمها `to`.

### علامات إعادة تسمية لا تكفي للتحويل
- `app/page.tsx` و`app/layout.tsx` يحتويان علامة QUVOTO وSEO ونطاق `quvoto.com` ومسارات `/pricing` و`/rewards` و`/login` و`/app`.
- `package.json` ما زال اسمه `voicequote`، وأوامر `deploy` و`preview` قادرة على تشغيل عملية نشر عند استدعائها.
- `.env.example` يعرّف إعدادات Gemini وLemon Squeezy وVAPID ومفاتيح Supabase، بالإضافة إلى إعدادات مدير QUVOTO.
- لم يظهر ملف قفل اعتماديات في جذر المستودع ضمن قائمة الملفات المفحوصة؛ وسير CI يستخدم `npm install`، كما أن بعض اعتماديات التطوير تستخدم `latest`. ينبغي تثبيت الإصدارات وتوفير lockfile قبل الاعتماد على نتائج بناء قابلة للتكرار.

لا ننسخ قيم مفاتيح أو أسرار إلى هذه الوثيقة. أسماء المتغيرات وحدها ليست أسرارًا.

## 3. CI والنشر

- `.github/workflows/ci.yml` يعمل على push إلى `main` وعلى pull request، ويستخدم Node.js 22، وينفذ `npm install` والاختبارين المحددين ثم `npm run build` باستخدام قيم اختبار تجريبية.
- `.github/workflows/deploy-cloudflare.yml` مهيأ للنشر عند push إلى `main` أو تشغيل يدوي. لا ينبغي تشغيله يدويًا خلال التحضير.
- لم يتم تشغيل build أو الاختبارات في بيئة تنفيذ محلية لهذه الجلسة؛ مراجعة الملفات ليست بديلًا عن نجاح CI الفعلي.
- لن يُفتح PR أو يُدمج الفرع دون طلب مستقل.

## 4. لقطة قاعدة البيانات — فحص قراءة فقط

- حالة المشروع المعلنة: `ACTIVE_HEALTHY`، PostgreSQL 17.6.1، المنطقة `ap-southeast-2`.
- يوجد 25 جدولًا في `public`. أعاد فحص العدّ السابق صفر صفوف لكل جدول من هذه الجداول، وأعاد `auth.users` صفر مستخدمين وقت الفحص. هذه لقطة وقتية لا تثبت غياب بيانات خارج هذه الجداول أو ظهور بيانات لاحقًا.
- توجد 17 migration مسجلة في Supabase، وتغطي أسماء منها عروض الأسعار والفواتير والفرق والإحالات والخصومات وسياسات الفوترة. لم نعثر على مجلد migrations في المستودع لمطابقة المصدر مع سجل الإنتاج.
- الجداول الحالية تتضمن: `profiles`, `business_profiles`, `customers`, `quotes`, `quote_photos`, `quote_templates`, `jobs`, `followups`, `invoices`, `subscriptions`, `usage`, `team_memberships`, `team_invites` وجداول الإحالات والخصومات والإشعارات والموافقات القانونية.
- بعض سياسات الجداول تعتمد على دوال داخل مخطط `app_private`، مثل `team_owner_id`، ودالة إنشاء عرض السعر تفوض إلى `app_private.create_quote`. يجب استخراج تعريفات هذه الدوال وأذوناتها ضمن سجل الاستعادة؛ لا تتوفر ملفات migration المصدرية في المستودع لتوثيق منشئها.

## 5. الأمان والصلاحيات

### RLS
- RLS مفعّل على الجداول العامة الـ25 كلها.
- FORCE RLS غير مفعّل على هذه الجداول في اللقطة الحالية.
- عدد سياسات `public` المرصود هو 59. كثير منها يربط `user_id` أو `owner_id` بالمستخدم الحالي أو بدالة مالك الفريق، لكن ذلك لا يثبت عزلًا صحيحًا على مستوى المكتب العقاري.
- لا توجد نتائج lint من مستشار Supabase الأمني وقت الفحص. هذا مؤشر محدود وليس شهادة أمان ولا بديلًا عن اختبار الصلاحيات تحت مستخدمين مختلفين.

### وظائف حساسة
- `app_find_user_id_by_email` و`apply_referral_reward` دالتان SECURITY DEFINER. أظهر الفحص أن `anon` و`authenticated` لا يملكان EXECUTE عليهما. إعداد `search_path` للدالة الأولى مثبت على `pg_catalog`، أما الثانية فمثبت على `public`; يلزم تضمين تعريفها وامتيازاتها في المراجعة قبل أي إعادة استخدام أو تعديل.
- يجب ألا تعتمد صلاحيات AqarFlow على إخفاء عناصر الواجهة فقط. كل استعلام وRPC وStorage policy يحتاج حدًا واضحًا بين مكاتب العقارات.

### Storage
- يوجد bucket باسم `business-logos` وآخر باسم `quote-photos`، وكلاهما معلّم `public=true`، ولا يحدد حدًا للحجم أو قائمة أنواع ملفات مسموحة.
- سياسة Storage الخاصة بـ`quote-photos` تسمح بـSELECT لدوري `anon` و`authenticated`. في bucket عام يمكن جلب الملفات عبر URL عام دون أن يعمل RLS كحاجز للقراءة العامة؛ يجب حسم ما إذا كانت صور العروض خاصة أم عامة قبل نقل المحتوى إلى صور العقارات والمرفقات.
- لم يُعثر على صفوف في `storage.objects` ضمن الفحص السابق، لكن هذا لا يغني عن الجرد عبر Storage API وتنزيل كل كائن عند أخذ النسخة الخارجية. يجب إعادة التحقق قبل اعتبار المخزن فارغًا.

### الأداء
أعاد مستشار الأداء 8 تحذيرات INFO عن مفاتيح أجنبية بلا فهرس تغطية، و3 تحذيرات WARN عن إعادة تقييم دوال auth داخل سياسات RLS، و29 ملاحظة عن فهارس غير مستخدمة. بعض ملاحظات الفهارس قد تنتج من قلة الاستخدام أو خمول المشروع؛ لا نحذف فهارس ولا نغير سياسات ضمن هذا التحضير.

## 6. النسخ الاحتياطي: الحالة والمانع

**الحالة: غير مكتمل — لا توجد نسخة خارجية تم إنشاؤها أو استعادتها واختبارها من خلال هذه الجلسة.**

موصل Supabase المتاح يتيح الاستعلام عن قاعدة البيانات وبيانات المشروع، لكنه لا يوفّر هنا تنزيل ملف `pg_dump` كاملًا قابلًا للتحقق، ولا عملية تنزيل جميع الملفات الثنائية من Storage إلى أرشيف خارجي. لذلك فإن نسخ أسماء الجداول أو نتائج SQL أو بيانات `storage.objects` لا يُعد نسخة احتياطية كافية.

قبل موافقة أي تغيير إنتاجي:
1. تصدير schema + data من PostgreSQL بواسطة Supabase CLI/`pg_dump` باستخدام بيانات اتصال سرية داخل بيئة موثوقة.
2. حفظ سجل migrations وتعريفات الدوال والـ triggers والسياسات والامتيازات.
3. جرد ملفات Storage عبر API وتنزيل بايتات الملفات نفسها مع manifest وchecksums.
4. حفظ إعدادات Auth القابلة للتصدير وملفات النشر، وحفظ الأسرار منفصلة داخل مدير أسرار؛ لا تُكتب كلمات المرور أو service-role keys داخل المستودع.
5. تشفير النسخة، وفحص أحجامها وchecksums، وتخزينها خارج حساب/مشروع المصدر.
6. استعادة تجريبية في بيئة موجودة ومصرح بها، ثم مطابقة الجداول والصفوف والسياسات والدوال والملفات. لا تنشأ قاعدة أو فرع جديد قبل عرض التكلفة وموافقة مستقلة.
7. تسجيل نتيجة اختبار الاستعادة وتاريخ النسخة وcommit المصدر، ثم طلب موافقة إنتاج مستقلة قبل أي migration.

## 7. قرارات ترحيل مؤقتة

- لا حذف أو إعادة تسمية أو تحويل للجداول الحالية.
- لا تغيير لـRLS أو Storage buckets أو الأسرار أو إعدادات Cloudflare.
- تصميم AqarFlow ككيانات مكاتب/مساحات عمل وعقارات وعملاء محتملين ومحادثات ومواعيد ومهام وسجل نشاط، مع `workspace_id` إلزامي في كل كيان مملوك لمكتب.
- يجب بناء سياسة عضوية المكتب والأدوار أولًا، ثم اختبارات تمنع قراءة/تعديل بيانات مكتب آخر.
- يفضّل نهج إضافة تدريجي: مخطط جديد على بيئة اختبار مصرح بها، ثم مراجعة migrations كملفات، مع إبقاء البيانات القديمة كما هي إلى أن تُراجع نتائج النسخ والاستعادة وتصدر موافقة ثانية.

## 8. سجل التغييرات المسموح به

هذه الوثيقة ومخطط التصميم التحضيري فقط. لا تغييرات تطبيقية أو بيانات قاعدة أو إعدادات إنتاج نفذت في هذا الفحص. لا تعني هذه الوثيقة الموافقة على الدمج أو النشر أو تنفيذ migrations.
