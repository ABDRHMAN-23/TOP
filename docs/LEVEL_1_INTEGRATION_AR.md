# المستوى الأول — تكامل AqarFlow / CRM / WhatsApp / اختبارات الوكيل

## ما يضيفه الفرع

- محرك المبيعات العقارية الحالي متصل الآن بمسار خادم مخططه هو `POST /api/aqarflow/sales`. المصادقة، وتحديد مساحة العمل، وقراءة العقارات محدودة العدد من قاعدة البيانات، وترتيب حتى 50 مرشحًا، ثم تمرير أفضل خمسة فقط إلى Gemini، والتحقق من مسودة الرد قبل إرجاعها.
- عند عدم وجود عقار مؤهل، يعيد المسار ردًا عربيًا حتميًا دون استدعاء Gemini ودون توكنات مدفوعة.
- واجهة عربية لمساعد المبيعات على `/aqarflow-assistant`، وواجهة مخزون على `/properties` مع API لإضافة العقارات وتعديلها وحذفها.
- إعداد Promptfoo في `promptfoo/aqarflow-sales.promptfooconfig.yaml` لاختبار عقد الرد والحقائق وحقن التعليمات ومسار عدم المطابقة.
- تكامل WhatsApp Cloud API على الخادم فقط: تبادل كود Meta، وتحقق ملكية رقم الهاتف ضمن WABA، والتحقق من توقيع Webhook، وتشفير الرمز، وتخزين أحداث مكررة بأمان، وإرسال نص مقيد بنافذة الخدمة ذات 24 ساعة.
- ملفات مقترحة لمخطط بيانات العقارات واستهلاك AI وWhatsApp. لا ينفّذ GitHub Actions هجرات SQL ولا تتصل هذه التغييرات بقاعدة البيانات من تلقاء نفسها.
- CI يشغّل اختبارات نواة المبيعات، ومحول WhatsApp، وعقود المهاجرة ثم بناء Next.js.

## قرار DeskcommCRM

تم فحص المستودع ووثائقه وترخيص MIT. لكنه تطبيق مستقل كامل (Next.js + Supabase + نظام نشر ذاتي على VPS/Docker + CRM ومحادثات وWAHA). لا يُعتبر مكتبة قابلة للنسخ الجزئي، ولا يصح دمجه فوق TOP دون قرار صريح بتبديل جذر التطبيق، وترحيل الهوية والمصادقة والمخطط ومزود النشر. هذا PR يضيف مجال عقاري وCRM عبر جداول مخصصة ضمن قاعدة Supabase الحالية، ولا يدعي أنه نسخ DeskcommCRM أو أنه دمجه كتطبيق أساس. إذا كان المطلوب التحويل الحرفي إلى DeskcommCRM، فهو عملية ترحيل منفصلة وتحتاج مستودعًا/نسخة عمل مستقلة.

## إعداد WhatsApp (خادم فقط)

أضف الأسرار إلى Cloudflare secrets / إعدادات الخادم ولا تحفظها في Git:

- `META_APP_ID`
- `META_APP_SECRET`
- `META_GRAPH_API_VERSION` — اختر إصدارًا مدعومًا من وثائق Meta في وقت التفعيل، وثبّته بصيغة `vXX.0`.
- `META_WEBHOOK_VERIFY_TOKEN` — قيمة عشوائية قوية للتحقق من Webhook.
- `META_TOKEN_ENCRYPTION_KEY` — مفتاح عشوائي Base64 يفك إلى 32 بايت.
- `SUPABASE_SECRET_KEY` أو `SUPABASE_SERVICE_ROLE_KEY` — وصول خادمي للجداول الجديدة.
- `AQARFLOW_WHATSAPP_WORKER_SECRET` (مطلوب لمسار المعالجة الآلي إذا فُعّل لاحقًا).

لا يوجد ربط حي قبل إعداد Meta Business/App، وتفعيل Embedded Signup، وتعيين Webhook URL، والصلاحيات والتحقق المطلوبين من Meta. لا توجد أسرار حقيقية في هذا PR.

## إعداد Gemini وPromptfoo

- `GEMINI_API_KEY` يبقى على الخادم فقط.
- النموذج الافتراضي هو `gemini-3.5-flash-lite` عبر `AQARFLOW_GEMINI_MODEL`.
- يشغّل الأمر `npm run eval:aqarflow:promptfoo` مجموعة التقييمات. يجب توفير `AQARFLOW_EVAL_URL` كرابط مسار المبيعات في بيئة تطوير، و`AQARFLOW_EVAL_COOKIE` كجلسة خاصة لحساب اختبار داخل مساحة عمل معزولة.
- لا تخزن Cookie في الملفات أو CI، ولا تشغّل التقييم مع جلسة إنتاج أو بيانات عملاء حقيقية. لم يتم تشغيل التقييم الحي ضمن هذا العمل.

## الهجرات والسلامة

طبّق `202610100002_aqarflow_ai_runtime.sql` ثم `202610100003_aqarflow_whatsapp_tech_provider.sql` ثم `202610100004_aqarflow_crm_inbox.sql` على قاعدة تطوير منفصلة بعد مراجعتها ومطابقة سجل هجرات قاعدة TOP الحقيقي. لا تُطبق أي هجرة على الإنتاج من هذا PR. تأكد أن مخطط `private` غير موجود ضمن Supabase Data API Exposed Schemas، ثم اختبر سياسات RLS والمالك وعضو الفريق وحساب من مساحة عمل أخرى.

## ما لا يثبته CI

نجاح البناء واختبارات الوحدة لا يعني اتصالًا حيًا مع Gemini أو Meta، ولا يثبت صحة الهجرة على القاعدة الفعلية أو سياسات RLS الحية. لا يزال إعداد Meta، وواجهة Embedded Signup، وصندوق رسائل متكامل مع تدفق الرد، وتقييم Promptfoo على بيئة حقيقية خطوات تشغيلية. لا دمج ولا نشر ولا تعديل قاعدة بيانات يحدث من هذا PR.
