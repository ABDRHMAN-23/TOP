# تنفيذ المستوى الأول — أساس CRM وWhatsApp وPromptfoo

## ما أُضيف في هذا الفرع

- محول WhatsApp Cloud API مستقل عن الواجهة، يتحقق من توقيع Webhook باستعمال HMAC-SHA-256.
- مسار ربط Meta يعيد تبادل كود Embedded Signup على الخادم فقط، ويتحقق من أن رقم الهاتف تابع إلى WABA المصرّح به، ثم يشترك في Webhooks قبل حفظ الاتصال.
- تُشفّر رموز Meta باستخدام AES-256-GCM بمفتاح خادم مستقل؛ لا تعاد الرموز في استجابات API ولا تحفظ كنص صريح.
- مسار Webhook يقرأ جسمًا محدود الحجم، ويتحقق من التوقيع قبل تحليل JSON، ويخزن الرسائل والحالات بمفاتيح تمنع تكرار الحدث.
- مسار الإرسال مقصور على مالك مساحة العمل، ويعمل فقط خلال نافذة خدمة العميل البالغة 24 ساعة من آخر رسالة واردة. إرسال القوالب المعتمدة خارج النافذة ليس منفذًا.
- لكل إرسال مفتاح idempotency؛ لا يعاد الإرسال تلقائيًا عندما تكون نتيجة الموفر غير مؤكدة، لتقليل خطر تكرار الرسالة.
- اختبار مستقل لمحول WhatsApp بلا اعتماديات إضافية.
- إعداد Promptfoo لاختبار API المبيعات بالعربية، وعقد الرد، ومحاولات حقن التعليمات، ومسار عدم المطابقة. التشغيل مقصود يدويًا ولا يدخل CI الافتراضي لأنه يحتاج إلى حساب اختبار وCookie جلسة.

## إعدادات البيئة المطلوبة

تُعرّف في إعدادات الخادم فقط، ولا تضاف إلى Git:

- META_APP_ID
- META_APP_SECRET
- META_GRAPH_API_VERSION — إصدار Graph API مثبت صراحة بصيغة vXX.0، ويجب اختياره من وثائق Meta وقت التفعيل.
- META_WEBHOOK_VERIFY_TOKEN — قيمة عشوائية قوية للتحقق من تحدي Webhook.
- META_TOKEN_ENCRYPTION_KEY — قيمة Base64 تفك إلى 32 بايت بالضبط؛ مثال التوليد: openssl rand -base64 32.
- SUPABASE_SECRET_KEY أو SUPABASE_SERVICE_ROLE_KEY — سر خادمي للجداول الجديدة.
- NEXT_PUBLIC_META_APP_ID و META_EMBEDDED_SIGNUP_CONFIG_ID ستحتاج إليهما واجهة Embedded Signup لاحقًا؛ هذا الفرع يجهز API الخادم لكنه لا يضيف شاشة الربط أو Facebook SDK.

## تطبيق قاعدة البيانات

الهجرة المقترحة هي supabase/migrations/202610100003_aqarflow_whatsapp_tech_provider.sql. لا تطبقها على الإنتاج مباشرة. سلسلة الهجرات في المشروع لم تكن متاحة كاملة عند الفحص؛ ادمجها بعد مراجعة الترتيب الفعلي في قاعدة تطوير منفصلة، ثم اختبر RLS والصلاحيات. الجداول الجديدة تسحب صلاحيات anon وauthenticated وتعطي الوصول إلى service_role فقط حتى تمر العمليات عبر المسارات التي تتحقق من المالك والتوقيع.

## Promptfoo

يتطلب ملف الإعداد وجود API المبيعات على المسار /api/aqarflow/sales، الذي تضيفه حزمة AqarFlow AI Integration v5 عند تطبيقها، ونقطة اختبار لا تحتوي على بيانات عملاء حقيقية. عرّف:

- AQARFLOW_EVAL_URL: رابط API المبيعات في بيئة تطوير.
- AQARFLOW_EVAL_COOKIE: قيمة Cookie جلسة مستخدم اختبار من مساحة عمل معزولة.

التشغيل: npx --yes promptfoo@0.124.1 eval -c promptfoo/aqarflow-sales.promptfooconfig.yaml

لا تضف AQARFLOW_EVAL_COOKIE إلى الملفات أو سجلات CI. استخدم مخزونًا معزولًا ولا تستخدم جلسة الإنتاج.

## قرار DeskcommCRM

DeskcommCRM تطبيق كامل، وليس حزمة مكون صغيرة. فحصنا بياناته ووثائقه: يعتمد Next.js وSupabase ويشمل CRM ومحادثات ووكيلًا، لكنه يتضمن أيضًا افتراضات نشر ذاتي على VPS وDocker وطبقة WhatsApp خاصة به. لذلك لا يصح نسخه داخل TOP كأنه مكتبة، أو جمع نظامي مصادقة وقاعدتي بيانات. تبنّيه كأساس يعني أن يكون fork مستقل هو التطبيق الجذري ثم نقل مجال العقارات إليه ومراجعة النشر والبيانات والاعتماديات. هذا الترحيل الجذري غير منفذ في هذا الفرع؛ أبقينا TOP منفصلًا ولم نحذف منه أو نستبدل صفحات المنتج القديمة.

## ما لم يكتمل

- لم تُكمل واجهة Embedded Signup أو تُختبر بحساب Meta حقيقي.
- لم يتم إعداد Meta App أو التحقق التجاري أو الصلاحيات/المراجعات اللازمة للإنتاج، ولم تُضف أي أسرار.
- لم تُطبق الهجرة على Supabase ولم تُغيّر البيانات.
- لم يُربط الحدث الوارد بمحرك المبيعات أو CRM inbox تلقائيًا؛ تُحفظ الأحداث كي تستهلكها طبقة معالجة منفصلة بعد تحديد مخطط المحادثات وحالة التسليم للموظف.
- إعداد Promptfoo لا يعمل قبل تركيب API المبيعات من حزمة v5، وإعداد Cookie ومخزون اختبار.
- لم يتم تشغيل بناء Next.js الكامل أو نشر التطبيق في هذا التغيير.

قبل الإنتاج: اختبر Meta حيًا، وعزل المؤسسات وRLS، وسياسات الرسائل والقوالب، ومراجعة الهجرة ومفتاح التشفير. كذلك يلزم worker/queue يستهلك الأحداث من received/queued، واختبار إعادة التسليم والرسائل المكررة وانتهاء الصلاحيات.
