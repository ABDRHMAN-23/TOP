# نموذج البيانات المقترح لـ AqarFlow AI — تصميم فقط

**الحالة:** مقترح مبدئي قابل للمراجعة؛ ليس migration ولا SQL جاهزًا للتطبيق.  
**المصدر:** جرد المستودع وقاعدة TOP بتاريخ 2026-10-09.  
**قاعدة الإنتاج:** مقفلة؛ لا إنشاء جداول أو تغيير سياسات الآن.

## 1. المبدأ الأساسي

AqarFlow هو CRM عقاري متعدد المكاتب. حدود الأمان الأساسية يجب أن تكون **المكتب/مساحة العمل (workspace)**، لا المستخدم وحده. قد ينتمي المستخدم إلى مكتب أو أكثر، وتختلف صلاحياته حسب عضويته في كل مكتب.

كل سجل أعمال تابع لمكتب يحمل `workspace_id`، وكل عملية قراءة/إنشاء/تعديل/حذف تتحقق من عضوية المستخدم ودوره داخل ذلك المكتب في قاعدة البيانات، وليس من اختيار الواجهة فقط.

## 2. الكيانات المقترحة

| الكيان | الغرض الأساسي | حقول/قيود مبدئية |
|---|---|---|
| `workspaces` | المكتب العقاري أو الشركة | id، name، slug، status، created_at |
| `workspace_members` | ربط المستخدم بالمكتب | workspace_id، user_id، role، status، invited_at، joined_at؛ قيد uniqueness على (workspace_id,user_id) |
| `properties` | العقارات المعروضة أو المدارة | workspace_id، code، title، property_type، purpose، price، currency، address/location، bedrooms/bathrooms، area، status، description، created_by |
| `leads` | العملاء المحتملون | workspace_id، assigned_to، name، phone، email، source، intent، budget_min/max، preferred_area، stage، next_follow_up_at، consent_status |
| `lead_property_matches` | ربط العملاء بالعقارات المرشحة | workspace_id، lead_id، property_id، score، explanation، created_at؛ لا تُخلط توصية AI مع قرار نهائي |
| `conversations` | سجل تواصل مع عميل محتمل | workspace_id، lead_id، channel، external_thread_id، status، last_message_at |
| `messages` | رسائل المحادثات | workspace_id، conversation_id، direction، provider_message_id، body، status، sent_at، error_code؛ تجنب تخزين أسرار التكامل |
| `appointments` | معاينات العقارات والاجتماعات | workspace_id، lead_id، property_id، assigned_to، starts_at، ends_at، status، location، notes |
| `tasks` | متابعات ومهام الموظفين | workspace_id، lead_id، property_id، assigned_to، created_by، title، due_at، status، priority |
| `notes` | ملاحظات داخلية | workspace_id، lead_id، property_id، author_id، body، visibility |
| `ai_runs` | تتبع عمليات الذكاء الاصطناعي | workspace_id، actor_id، feature، model، status، latency_ms، token_usage عند توفره، cost_estimate، created_at |
| `integration_connections` | حالة تكاملات المكتب | workspace_id، provider، external_account_id، status، scopes، last_checked_at؛ السر الحقيقي في مخزن أسرار، لا نص عادي في هذه الجدول |
| `activity_events` | سجل تدقيق الأعمال المهمة | workspace_id، actor_id، action، entity_type، entity_id، minimal metadata، created_at؛ لا تسجل tokens أو محتوى خاصًا بلا ضرورة |
| `workspace_usage` | قياس استخدام وموازنته | workspace_id، period_start، metric، quantity؛ القيود تمنع تكرار نفس metric للفترة |

هذه قائمة تصميم، وليست قرارًا نهائيًا بشأن أنواع البيانات أو جميع الأعمدة أو الـ constraints. يلزم حسم نموذج التسعير، وتكامل الرسائل، ومجالات العقارات المستهدفة قبل إعداد migration.

## 3. الأدوار ونطاق الصلاحيات

الأدوار المقترحة كبداية:
- **owner:** إعداد المكتب والفوترة وإدارة الأعضاء وجميع بيانات المكتب.
- **admin:** إدارة الفريق والعقارات والعملاء والإعدادات، دون صلاحيات حسابية مخصصة للمالك إلا إذا تقرر خلاف ذلك.
- **manager:** إدارة العقارات والعملاء والتوزيع والمهام والتقارير.
- **agent:** السجلات المسندة إليه وما تسمح به سياسة المكتب.
- **viewer:** قراءة محدودة فقط.

لا يجب اعتبار أسماء الأدوار أو وجودها في JSON دليل صلاحية. يجب أن يُستخرج الدور من عضوية موثوقة في قاعدة البيانات، مع منع المستخدم من تعيين `workspace_id` لمكتب لا ينتمي إليه.

## 4. متطلبات RLS والقيود

قبل قبول النموذج:
1. تفعيل RLS لكل جدول من جداول المكتب الجديدة.
2. صياغة سياسات SELECT/INSERT/UPDATE/DELETE مع اختبار دورين من مكتبين مختلفين.
3. إضافة قيود FK تربط سجل الأعمال بالمكتب الصحيح. حيث تسمح البنية، استخدم مفاتيح مركبة لضمان أن lead/property/conversation/task يشير إلى سجل في المكتب نفسه، لا مجرد UUID صحيح.
4. تحديد دور مالك الجداول وامتيازات `anon` و`authenticated` و`service_role` بوضوح؛ لا تمنح `service_role` للمتصفح.
5. أي دالة SECURITY DEFINER تستخدم `search_path` مثبتًا وآمنًا، وتؤهل أسماء الكائنات بالمخطط، وتحصر EXECUTE على الأدوار المطلوبة فقط.
6. منع تحديث `workspace_id` أو `created_by` من المستخدم العادي بعد الإنشاء، إلا إذا كانت هناك عملية نقل موثقة ومصرح بها.
7. اختبار الوصول عبر REST وRPC وStorage مباشرة، لا من خلال الواجهة فقط.
8. إضافة اختبارات فشل: مستخدم من مكتب A يقرأ/يكتب معرف سجل من مكتب B، عضو موقوف يحاول الوصول، دور viewer يحاول التعديل، ومستخدم مجهول يحاول جلب ملف خاص.

## 5. التعامل مع الجداول الحالية

| الجداول الحالية | القرار المبدئي | السبب |
|---|---|---|
| `profiles` | مراجعة وإعادة استخدام الهوية عند الحاجة | لا تجعل ملف المستخدم بديلًا عن عضوية المكتب |
| `business_profiles` | لا تحولها مباشرة إلى `workspaces` | مرتبطة بالمستخدم وتحتوي إعدادات نشاط المقاول؛ يلزم فحص القيود والمراجع |
| `team_memberships` و`team_invites` | لا تعاد تسميتها الآن | نموذجها الحالي يعتمد owner/member وقد لا يغطي عضويات متعددة المكاتب بأمان |
| `customers` | لا تُحوّل مباشرة إلى leads | العميل الحالي مرتبط بالمقاول؛ lead يحتاج pipeline ومصدر ومالك وموافقة تواصل |
| `jobs` و`followups` | لا يعاد استخدامهما بلا مطابقة | دلالتهما الحالية مرتبطة بعروض العمل والمواعيد اللاحقة لها |
| `quotes` و`invoices` و`quote_photos` و`quote_templates` | إبقاؤها كما هي خلال مراحل التحضير | هي قلب VoiceQuote وقد تؤثر على الروابط العامة والـ PDF والوظائف الحالية |
| `subscriptions` و`usage` | مراجعة نموذج الفوترة قبل الربط | البيانات الحالية مبنية على user_id والاستخدام متعلق بعدد عروض الأسعار |
| `events` و`notifications` و`legal_consents` | تقييمها لإعادة الاستخدام بعد حصر الغرض والصلاحيات | لا تخلط سجل تدقيق CRM بسجل أحداث استخدام قديم دون فصل الاحتفاظ والوصول |
| جداول الخصومات والإحالات | معزولة كميزات QUVOTO حتى اتخاذ قرار المنتج | لا تعتمد عليها لمتطلبات مبيعات عقارية دون تعريف متطلبات جديدة |

**ممنوع حذف أي جدول قديم أو إعادة استخدامه دلاليًا لمجرد أن الاستعلام أعاد صفر صفوف في لقطة زمنية.**

## 6. خطة تنفيذ آمنة بعد اكتمال النسخ الاحتياطي

1. إكمال النسخة الخارجية واختبار استعادتها، وجرد جميع ملفات Storage.
2. توفير مصدر migrations المفقود ومقارنته بسجل Supabase.
3. اعتماد نموذج المكتب والأدوار والفوترة ومصدر leads وتكامل التواصل.
4. إنشاء migrations إضافية على بيئة اختبار مصرح بها فقط، بعد مراجعة التكلفة وموافقة مستقلة إذا كان ذلك سينشئ موردًا مدفوعًا.
5. بناء الاختبارات أولًا: RLS وعزل المكتب، الصلاحيات، حدود الاستخدام، وحالات فشل تكامل الرسائل.
6. تنفيذ الواجهات والـ API على فرع GitHub المنفصل وتجاوز الميزات القديمة تدريجيًا دون تغيير `main`.
7. مقارنة diff وتشغيل CI ومراجعة مخرجات الفحص الأمني.
8. تقديم خطة نشر/رجوع ونتائج الاختبارات، ثم طلب تأكيد منفصل وصريح لأي تغيير إنتاجي.

## 7. قرارات تحتاج حسمًا قبل كتابة migrations

- هل كل مكتب عقاري يملك مساحة عمل واحدة أم يمكن أن يملك عدة فروع؟
- ما قناة التواصل الأساسية في المرحلة الأولى: مكالمات/واتساب/بريد/رسائل داخلية؟
- هل يرسل الوكيل رسائل تلقائيًا، أم يكتب مسودة ولا يرسل إلا بعد موافقة الموظف؟
- هل المنصة multi-tenant باشتراك المكتب أم باشتراك كل مستخدم؟
- هل صور العقارات عامة للنشر أم مستندات داخلية خاصة؟
- ما الدول/الأسواق الأولى للعقارات وما الحقول المحلية اللازمة؟

هذه الأسئلة لا تمنع استكمال مراجعة المستودع، لكنها تمنع وضع مخطط نهائي قد يفرض قرارًا تجاريًا أو أمنيًا غير متفق عليه.
